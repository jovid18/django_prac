# プルリクエストの作成

## 前提

- ベースブランチは **`main`**。
- **タイトルも本文も日本語**で書く（接頭辞の `feat:` などだけ英語）。
- `main` はブランチ保護されており、**`backend` と `frontend` の CI が通らないとマージできない**。
- マージは **Squash merge**。PR のタイトルがそのまま `main` の履歴に残るので、タイトルを丁寧に書く。

## 手順

### 1. 状態を確認する

```bash
git branch --show-current
git status --short
git log origin/main..HEAD --oneline
```

- `main` にいる場合は PR を作れない。ユーザーに確認する。
- **未コミットの変更が残っていないか確認する。** あれば `commit` スキルで先に片付ける。
- push されていなければ push する: `git push -u origin HEAD`

### 2. 差分を読む

```bash
git diff origin/main...HEAD --stat
git diff origin/main...HEAD
```

**差分を読まずに本文を書かない。** コミットメッセージの寄せ集めではなく、
**レビュアーが読む順に再構成する。**

### 3. 本文を組み立てる

`gh pr create` に渡す前に、以下のテンプレートで組み立てる。
**該当しない節は省いてよい。** 空の見出しを残さない。

```markdown
## 概要

<この PR で何が変わるのかを 2〜3 行。レビュアーが最初に読む部分。>

## 背景 / なぜ必要か

<この変更をする理由。issue や設計ドキュメントがあれば参照する。
 自明な場合は省略してよい。>

## 変更内容

- <差分の要点を箇条書き。ファイル単位ではなく、意味の単位で書く>
- <例: 「図書館の検索 API を追加（bbox / 喫煙区分 / 件数上限）」>

## 設計上の判断

<当初の計画から変えた点があれば、変える前の案と変えた理由を書く。
 レビューで最も議論になる部分なので、先回りして書いておく。
 なければこの節ごと省く。>

## 動作確認

<実際に何を確認したかを、再現できる形で書く。>

```
（実行したコマンドと結果）
```

- [ ] テスト: <件数>
- [ ] lint / format
- [ ] マイグレーション整合（`makemigrations --check`）
- [ ] ローカルで実際に動かした

## レビューで見てほしい点

- <特に見てほしい箇所。判断に迷った箇所。>
- <「ここは好みが分かれると思う」も書いてよい>

## 関連ドキュメント

- `docs/xx-yyy.md`

## 補足

<スコープ外にしたこと、既知の制約、次にやる予定など。>
```

**書き方の指針**

| 原則 | 中身 |
|---|---|
| **レビュアーの時間を節約する** | 差分を読めば分かることを繰り返さない。差分から読み取れないことを書く |
| **判断を先回りして説明する** | 「なぜこの実装にしたか」を書いておくと往復が減る |
| **動作確認は再現可能な形で** | 「動作確認しました」だけでは意味がない。コマンドと結果を貼る |
| **不安な箇所を隠さない** | 自信がない箇所は「レビューで見てほしい点」に書く |
| **スコープ外を明記する** | 「これはこの PR でやらない」と書いておくと指摘が減る |

### 4. タイトルを決める

```
<type>(<scope>): <日本語の要約>
```

- **Squash merge で `main` の履歴に残る。** 一行で何をしたか分かるようにする。
- 50 字程度まで。

例: `feat(libraries): 図書館モデルと検索 API、東京都 490 件のシードデータ`

### 5. PR を作成する

**本文は HEREDOC で渡す。**

```bash
gh pr create --base main --title "<タイトル>" --body "$(cat <<'EOF'
（組み立てた本文）
EOF
)"
```

`gh` が未認証なら、ユーザーに `gh auth login` を依頼する。
それも難しい場合は、**組み立てた本文をそのまま提示して**ブラウザで作ってもらう。
`git push` 時に表示される `https://github.com/<owner>/<repo>/pull/new/<branch>` を案内する。

### 6. CI を確認する

作成後、CI の結果まで見届ける。

```bash
gh pr checks --watch
```

`gh` が使えない場合は API で確認する（public リポジトリなら認証不要）。

```bash
curl -sS "https://api.github.com/repos/<owner>/<repo>/actions/runs?per_page=3"
```

**落ちていたら原因を特定して報告する。** 「CI が落ちました」だけで終わらせない。

### 7. 報告する

- PR の URL
- タイトル
- CI の結果（`backend` / `frontend` / `deploy`）
- マージ待ちか、修正が必要か

## やらないこと

- **ユーザーの許可なくマージしない。** マージはユーザーの判断。
- CI の結果を確認せずに「完了しました」と報告しない。
- 未コミットの変更を残したまま PR を作らない。
- テンプレートの見出しだけ並べて中身を書かない。**書けない節は削る。**
