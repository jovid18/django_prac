# プルリクエストの作成

## 前提

- ベースブランチは **`main`**。
- **タイトルも本文も日本語**で書く（接頭辞の `feat:` などだけ英語）。
- `main` はブランチ保護されており、**`backend` と `frontend` の CI が通らないとマージできない**。
- マージは **Squash merge**。PR のタイトルがそのまま `main` の履歴に残るので、タイトルを丁寧に書く。

## 手順

### 1. 状態を確認する

```bash
git branch --show-current
git status --short
git log origin/main..HEAD --oneline
```

- `main` にいる場合は PR を作れない。ユーザーに確認する。
- **未コミットの変更が残っていないか確認する。** あれば `commit` スキルで先に片付ける。
- push されていなければ push する: `git push -u origin HEAD`

### 2. 差分を読む

```bash
git diff origin/main...HEAD --stat
git diff origin/main...HEAD
```

**差分を読まずに本文を書かない。** コミットメッセージの寄せ集めではなく、
**レビュアーが読む順に再構成する。**

### 3. 本文を組み立てる

> ## ★ 本文は短くする。全体で 40 行以内を目安にする。
>
> **長い PR 本文は読まれない。** 読まれなければ書いていないのと同じ。
> 差分は PR 画面に並んでいるので、**差分を見れば分かることを書かない。**
> 表・長いコードブロック・チェックボックスの羅列は基本的に不要。数字だけ書く。

**必須は 3 節だけ。**

```markdown
## 概要

<2〜3 行。この PR で何が変わるのか。>

## 変更内容

- <意味の単位で 3〜6 個。ファイル単位で列挙しない>

## 動作確認

```
<テスト件数、lint、実際に叩いた結果を数行で>
```
```

**以下は「書くことがあるときだけ」足す。無いなら節ごと消す。**

| 節 | 足す条件 |
|---|---|
| `## 設計上の判断` | **当初の計画から変えた**、または**選択肢があった**とき。変える前の案と理由を各 2〜3 行で |
| `## レビューで見てほしい点` | 判断に迷った箇所、自信がない箇所があるとき。2〜3 個まで |
| `## 補足` | スコープ外にしたこと、既知の制約、次にやる予定 |
| `## 関連` | 参照すべき `docs/` があるとき。1 行で十分 |

**背景の節は作らない。** 必要なら「概要」に 1 行足す。

**書き方の指針**

| 原則 | 中身 |
|---|---|
| **短く書く** | 40 行以内。長い本文は読まれない。読まれなければ書いていないのと同じ |
| **差分を繰り返さない** | ファイル一覧・行数・実装の説明は PR 画面に出ている。**差分から読み取れないことだけ**書く |
| **判断を先回りして説明する** | 「なぜこの実装にしたか」を 2〜3 行。長くなるなら `docs/` に書いて参照する |
| **動作確認は数字で** | 「動作確認しました」では意味がない。件数と結果を数行で |
| **不安な箇所を隠さない** | 自信がない箇所は「レビューで見てほしい点」に。ただし 2〜3 個まで |

**削るときの優先順位**（長くなったら上から削る）

1. 実装の詳細な説明 → 差分を見れば分かる
2. 表 → 箇条書きにする
3. 背景の長い説明 → `docs/` に書いて 1 行で参照する
4. チェックボックスの羅列 → 結果の数字 1 行にまとめる

### 4. タイトルを決める

```
<type>(<scope>): <日本語の要約>
```

- **Squash merge で `main` の履歴に残る。** 一行で何をしたか分かるようにする。
- 50 字程度まで。

例: `feat(libraries): 図書館モデルと検索 API、東京都 490 件のシードデータ`

### 5. PR を作成する

**本文は HEREDOC で渡す。**

```bash
gh pr create --base main --title "<タイトル>" --body "$(cat <<'EOF'
（組み立てた本文）
EOF
)"
```

`gh` が未認証なら、ユーザーに `gh auth login` を依頼する。
それも難しい場合は、**組み立てた本文をそのまま提示して**ブラウザで作ってもらう。
`git push` 時に表示される `https://github.com/<owner>/<repo>/pull/new/<branch>` を案内する。

### 6. CI を確認する

作成後、CI の結果まで見届ける。

```bash
gh pr checks --watch
```

`gh` が使えない場合は API で確認する（public リポジトリなら認証不要）。

```bash
curl -sS "https://api.github.com/repos/<owner>/<repo>/actions/runs?per_page=3"
```

**落ちていたら原因を特定して報告する。** 「CI が落ちました」だけで終わらせない。

### 7. 報告する

- PR の URL
- タイトル
- CI の結果（`backend` / `frontend` / `deploy`）
- マージ待ちか、修正が必要か

## やらないこと

- **ユーザーの許可なくマージしない。** マージはユーザーの判断。
- CI の結果を確認せずに「完了しました」と報告しない。
- 未コミットの変更を残したまま PR を作らない。
- テンプレートの見出しだけ並べて中身を書かない。**書けない節は削る。**
